What Is Percent-Encoding?

Percent-encoding (also called URL encoding) represents unsafe or reserved characters as a % followed by two hexadecimal digits — the character's byte value in UTF-8. A space becomes %20, an ampersand becomes %26. It exists because URLs can only reliably contain a limited set of ASCII characters; everything else has to be escaped to travel safely through browsers, servers, and links.

encodeURIComponent vs encodeURI: The Real Difference

encodeURIComponent escapes almost everything that isn't a letter, digit, or - _ . ~ — including / ? & = # — because it assumes you're encoding one isolated piece of a URL, like a query value. encodeURI assumes you already have a complete, structured URL and leaves : / ? & = # alone since removing them would break the URL's syntax. Mixing the two up is one of the most common URL-encoding bugs.

Why Spaces Sometimes Become + Instead of %20

Standard percent-encoding always turns a space into %20 — that's what encodeURIComponent and encodeURI both produce. The + shorthand for spaces comes from a separate, older convention: application/x-www-form-urlencoded, the format browsers use when submitting an HTML form. It's not "more standard" or "less standard" than %20 — it's a different encoding used in a different context, and the two aren't always interchangeable.

Common Use Cases

Encode a value before appending it to a query string (?q= plus a user's search term), encode a path segment that might contain spaces or symbols, or encode data being embedded inside another URL (like a redirect target passed as a parameter). Decoding is just as common — reading values back out of a query string, or making a logged, encoded URL human-readable again.

Best Practices to Avoid Mistakes

  • Never encode a string twice — it turns every % into %25 and corrupts the result
  • Use URI Component mode for query values and path segments, Full URI mode only for a complete link
  • Don't hand-roll + for spaces unless you're specifically building form-encoded data
  • Decode before reading a value, encode right before inserting it into a URL — not earlier

Frequently Asked Questions

What's the difference between encodeURIComponent and encodeURI?

encodeURIComponent escapes every character that isn't safe inside a single URI component — including /, ?, &, =, and # — so it's the right choice for a query parameter value or a path segment. encodeURI is for encoding a complete URI and deliberately leaves structural characters like :, /, ?, &, =, and # unescaped, since they still need to work as URL syntax.

Why do some forms turn spaces into + instead of %20?

That's the application/x-www-form-urlencoded convention used by HTML form submissions, not standard percent-encoding. Percent-encoding itself always represents a space as %20 — encodeURIComponent and encodeURI both do this. The + shorthand only applies inside form-encoded query strings and request bodies.

Why did decoding fail with an error?

decodeURIComponent and decodeURI throw a URIError when they hit malformed percent-encoding, such as a lone % that isn't followed by two valid hex digits, or an incomplete multi-byte UTF-8 sequence. This tool catches that error and shows a friendly message instead of crashing.

Is it safe to encode an already-encoded string?

No — encoding an already-encoded string turns every existing % into %25, corrupting the result. Only encode raw, unencoded text, and only decode a string once to get back the original.

What characters are safe to leave unencoded in a URL?

Unreserved characters — letters, digits, and - _ . ~ — are always safe and never get encoded. Reserved characters like / ? & = # : have structural meaning and are only left alone by encodeURI, not by encodeURIComponent.

Does this tool send my data anywhere?

No. Encoding and decoding happen entirely in your browser using JavaScript's built-in functions. Nothing you type is ever sent to a server or stored.
